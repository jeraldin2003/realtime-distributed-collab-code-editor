# P1-S6 — User cap

**Depends on:** P1-S5
**Goal:** The server enforces `MAX_USERS`. Clients show `N / MAX` and a clear "Room is full" state.

## Build
1. `backend/src/connectionLimiter.ts`: pure module, no network. API such as `tryAdd(id)`, `remove(id)`, `count()`. `remove` must be safe when called twice or for unknown ids.
2. Unit tests: allows up to max, rejects next, frees a slot on remove, double remove is safe.
3. Enforce in the Hocuspocus connection hook for `DOC_NAME` (verify hook name/signature/rejection mechanism in the installed version). Ensure the slot is released on disconnect and on failed connection.
4. `GET /status` → `{ users, maxUsers }` with CORS.
5. Client: fetch `/status` for `maxUsers`; header shows `N / MAX` (N from awareness or `/status`, pick one and note it in `DECISIONS.md`).
6. Rejection handling: when the server rejects because the room is full, the client stops retrying aggressively and shows a "Room is full" screen with a manual "Try again" button. Verify how the provider surfaces rejection (grounding skill); do not guess event names.
7. Integration test: with `MAX_USERS=1`, the second client is rejected; after the first disconnects, a new client is accepted.

## Files (expected)
`backend/src/{connectionLimiter.ts,server.ts,config.ts}`, tests, `frontend/src/collab/*`, `frontend/src/components/{Header.tsx,RoomFull.tsx}`

## Acceptance
- With `MAX_USERS=2`, a third tab shows "Room is full"; closing a tab then clicking "Try again" lets the third in.
- `/status` reports correct numbers.
- Limiter unit tests and cap integration test pass.
- Server logs a reject event with the current count.

## Verify
Run backend with `MAX_USERS=2`; test with 3 tabs. Run all checks.

## Do NOT
Cap by IP, accounts, queues, a waiting room.
